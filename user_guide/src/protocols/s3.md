# S3

`s3://` speaks to AWS S3 and to everything that imitates it: MinIO, Ceph,
Wasabi, Backblaze B2's S3 endpoint, a NAS with an object gateway.

```
mpt cp report.pdf "s3://reports/2026/"
mpt cp "s3://bucket/import/data.csv?endpoint=https://minio.example.com" ./
mpt ls "s3://bucket/import/?endpoint=https://minio.example.com&region=eu-central-1"
```

## Bucket and key

The path is `bucket/key`: the first segment is the bucket, the rest is the key.
Keys are flat (the slashes in them are just characters), but everything treats
them as paths, so the [trailing
slash](../getting-started/addressing.md#where-a-file-lands)
behaves as it does elsewhere: `s3://bucket/reports/` yields the key
`reports/report.pdf`.

A key is stored exactly as named, including characters such as `%`, `#`, `[`
or spaces, and the names `mpt ls` shows fetch those objects again. A key with
an empty segment (`a//b`), a `.` or `..` segment, or a control character is
refused as an invalid URL.

`mpt ls` lists with a delimiter, so common prefixes appear as directories:

```
$ mpt ls "s3://bucket/reports/"
d            -  2025
d            -  2026
-        40000  index.csv
```

## Non-AWS servers

Three options usually do it:

| Option | Configuration | Meaning |
|---|---|---|
| `?endpoint=<url>` | `[s3] endpoint` | the server, when it is not AWS |
| `?region=<r>` | `[s3] region` | the region; many servers accept anything |
| `?path_style=true` | `[s3] path_style` | `https://host/bucket/key` instead of `https://bucket.host/key` |

Path-style addressing is what most self-hosted servers need, because
virtual-host style requires a wildcard certificate and a DNS entry per bucket.
If a bucket "does not exist" against MinIO, this is the first thing to set.

```toml
[s3]
endpoint   = "https://minio.example.com"
region     = "eu-central-1"
path_style = true
```

With that in the configuration, a bare `s3://bucket/key` reaches the right
server. `?insecure=true` covers a self-signed certificate on it.

## Credentials

In order of precedence:

1. **`user:pass@` in the URL**: the access key and secret. Convenient for a
   one-off, and [visible in `ps`](../trust/connections.md#passwords-in-the-process-list).
2. **`[s3] access_key_id` and `secret_access_key`** in the configuration, each
   taking a [credential reference](../configuration/credentials.md).
3. **The standard environment variables**: `AWS_ACCESS_KEY_ID`,
   `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_REGION`,
   `AWS_ENDPOINT_URL`.

## Single sign-on and roles

Long-lived access keys are what SSO replaces. With the `s3-aws-auth` feature,
credentials can come from the full AWS chain instead: the SSO cache that
`aws sso login` fills, the profiles in `~/.aws/config`, AssumeRole, web
identity, and the instance metadata service.

```
cargo build --release --features s3-aws-auth

mpt cp report.pdf "s3://bucket/reports/?profile=prod"     # a named AWS profile
mpt cp report.pdf "s3://bucket/reports/?aws_chain=true"   # the chain, no AWS profile
```

`?profile=` here is an **AWS profile** from `~/.aws/config`, not an `mpt://`
profile from the configuration file; the two are unrelated. The chain is used
**only** when an AWS profile is named (`?profile=`, `[s3] profile` or
`$AWS_PROFILE`) or `?aws_chain=true` asks for it. Nothing reaches for the
instance metadata service unasked, since on some machines it would answer
with credentials you did not intend to use.

Explicit keys always win over the chain.

## Atomic finishing and directories on S3

**Atomic finishing is unnecessary.** An object appears only when its upload is
complete, so there is no window in which a half-written object carries the
final name. `mpt` therefore does not rename on S3, and
[`--no-atomic`](../guide/reliability.md#a-file-appears-only-when-it-is-whole)
changes nothing there. It also means `--resume` does not apply: an interrupted
upload leaves nothing to continue from.

**Directories do not exist.** A tree copy to S3 works, and creating the
"directories" is a no-op, because a key containing slashes is all a directory
ever was. An empty directory on the source therefore has no counterpart on S3,
the one place where a tree copy is not a faithful reproduction.

## Uploads

Uploads buffer **10 MiB** at a time. A payload that fits in that buffer is sent
as a single `PUT`; anything larger switches to a multipart upload of 10 MiB
parts, up to eight of them in flight, so a stream of unknown length can be sent
without holding all of it. A multipart upload that fails, whether in a part or
in completing it, is aborted rather than leaving parts behind for a lifecycle
rule to clean up; so is one that is cancelled, as far as the abort can still
reach the server before `mpt` exits.

## Timeouts on S3

[`--timeout`](../guide/copying.md#time-limits) is an inactivity limit here too,
with one granularity to know about. A download may take as long as it needs, as
long as the server never pauses for longer than the limit. An upload counts its
progress per request: the reply to each `PUT`, which carries at most one 10 MiB
part, has to arrive within the limit. On a line slower than about 10 MiB per
`--timeout` seconds, raise the limit.
