# Named targets

A profile gives a recurring endpoint a name. Instead of

```
mpt cp report.pdf "sftp://deploy@srv.example.com/data/incoming/?key=~/.ssh/prod_ed25519&hostkey=SHA256:f29GJDwDP5hekqa22VhNdaNPBM+q6AzG3FvQaBCJnmg&timeout=120"
```

you write

```
mpt cp report.pdf mpt://prod/incoming/
```

`mpt://<name>/<path>` works anywhere a URL is expected: as a source, as a
target, in `ls`, in a [job list](../guide/job-lists.md). The scheme `mpt://`
exists for exactly this and collides with nothing.

## Defining one

```toml
[profiles.prod]
url         = "sftp://deploy@srv.example.com/data/"
key         = "~/.ssh/prod_ed25519"
hostkey     = "SHA256:f29GJDwDP5hekqa22VhNdaNPBM+q6AzG3FvQaBCJnmg"
timeout     = 120
hash        = "blake3"

[profiles.archive]
url        = "s3://archive-bucket/reports/"
endpoint   = "https://minio.example.com"
path_style = true

[profiles.boss]
url     = "mailto:boss@example.com"
subject = "Report"
```

`url` is the only required key. Everything else falls into two groups:

- **Four reserved keys** set transfer options for that endpoint: `sign`,
  `hash`, `atomic`, and `password` (which takes a [credential
  reference](credentials.md)).
- **Everything else becomes a URL option.** `key`, `hostkey`, `timeout`,
  `endpoint`, `path_style`, `subject` above are not a fixed list that `mpt`
  knows about — they are simply appended to the profile's URL. A profile can
  therefore carry any option its scheme understands, including ones added
  later, and a typo shows up as an option the protocol ignores rather than as a
  configuration error.

A key that takes several values may be written as a list:

```toml
[profiles.prod]
url     = "sftp://deploy@srv.example.com/data/"
hostkey = ["SHA256:f29GJDwDP5he…", "SHA256:2mGf4C1Pq0Xk…"]   # during a key rotation
```

## Seeing what is defined

```
$ mpt profiles
mpt://boss  mailto:boss@example.com?subject=Report
mpt://prod  sftp://deploy@srv.example.com/data/?hostkey=SHA256:f29GJDwDP5hekqa22VhNdaNPBM+q6AzG3FvQaBCJnmg&key=~/.ssh/prod_ed25519&timeout=120
    hash   blake3
```

Each profile is shown as the URL it stands for, with the reserved keys on
their own line beneath. Passwords are masked. This is the quickest way to
check that a profile expands to what you meant, and it makes no connection.

## Paths, and where they end up

The path of the reference is appended to the profile's own path:

| Reference | Becomes |
|---|---|
| `mpt://prod` | `sftp://deploy@srv.example.com/data/` |
| `mpt://prod/` | the same |
| `mpt://prod/incoming/` | `…/data/incoming/` |
| `mpt://prod/incoming/x.pdf` | `…/data/incoming/x.pdf` |

The [trailing-slash rule](../getting-started/addressing.md#the-trailing-slash-decides-where-a-file-lands)
applies to the result, as always.

A reference cannot climb out of the profile's path:

```
$ mpt ls "mpt://prod/../etc/"
error: configuration: mpt://prod/../etc/: invalid URL: unsafe file name '..': refers to a directory
```

That matters when the path comes from somewhere else — a job list generated by
another program, a CI variable. `mpt://prod/` is then a boundary, not just an
abbreviation.

## Overriding a profile

Options on the reference win over the profile's own:

```
mpt cp report.pdf "mpt://prod/incoming/?timeout=300"     # this one transfer may take longer
```

That is the general rule from [the previous
page](file.md#what-wins-over-what): the more specific the place, the more it
counts. Note that this also puts a profile above a command-line flag, since the
profile belongs to one endpoint and the flag to the whole run:

```
$ mpt --timeout 7 ls mpt://prod/     # → timeout=120, the profile's value
```

The reserved keys behave the other way round, because they are run-wide
settings rather than endpoint options: `--hash sha256` beats `hash = "blake3"`,
and `--no-atomic` cannot be undone by `atomic = true`.

## A profile per relationship, not per command

Profiles pay off where an endpoint carries knowledge that is tedious and
error-prone to repeat — a pinned host key, a specific key file, a non-standard
S3 endpoint, a subject line. Some patterns that work well:

```toml
# The partner whose FTP server needs implicit TLS and a password from the key store
[profiles.partner]
url      = "ftps://upload@ftp.partner.example/in/"
tls      = "implicit"
passive  = true
password = { keyring = "mpt/partner-ftp" }

# The release bucket, where everything must be signed
[profiles.releases]
url  = "s3://releases/artifacts/"
sign = "ssh:~/.ssh/release_ed25519"
hash = "sha256"

# The archive host, patient because it is on the other side of a slow link
[profiles.archive]
url     = "sftp://archive@nas.example.com/vol1/backups/"
key     = "~/.ssh/archive_ed25519"
timeout = 600
```

With `sign` in the profile, a copy to `mpt://releases/` is signed whether or not
whoever typed the command remembered to ask for it: the decision is recorded in
one place instead of in everyone's habits.

## Limits

- **Profiles do not chain.** A profile's `url` may not be another `mpt://`
  reference. One level of indirection is a convenience; two is a maze.
- **`./mpt.toml` may not define profiles.** A file in the working directory
  can tune how a transfer runs, never where it goes; see
  [the file in the working directory](file.md#the-file-in-the-working-directory).
- **An unknown name is an error**, and the message says what does exist:

  ```
  $ mpt ls mpt://nosuch/
  error: configuration: no profile 'nosuch' (known: boss, prod)
  ```
